# Concept

## このアプリの狙い

Plamo Design Feedback AIは、ランナー画像または架空の部品特徴データを入力し、切り出し前のリスクと改善案を見える化する学習用プロトタイプです。

完成後の見た目ではなく、ランナーから切り出す時点の不安、迷い、破損リスク、ゲート跡をユーザー体験として捉え、設計・金型・説明書・ユーザー体験の改善につなげることを狙いとしています。

このプロトタイプでは実在商品や公式データは使わず、すべて架空のキット名、架空の部品、架空のレビュー文を使用しています。

## 入力データの例

CSVには以下の列を持つフィードバックを入力します。

| 列名 | 内容 |
| --- | --- |
| feedback_id | フィードバックID |
| kit_name | 架空キット名 |
| part_area | 対象部位 |
| inspection_phase | 検査フェーズ |
| feedback_text | 日本語の自由記述レビュー |
| user_level | ユーザーレベル |
| created_at | 作成日 |

入力例:

```text
肩の関節がかなり固く動かしたときに白化しそうで怖かった。
細長いA1パーツが薄くランナーから切り出すときに折れそうだった。
説明書の工程が少し分かりにくく左右のパーツを間違えそうになった。
```

## 分析の流れ

1. `data/sample_feedback.csv` を読み込む。
2. `inspection_phase` でランナー状態・組立前のフィードバックを主対象として扱う。
3. `feedback_analyzer.py` でキーワードベースの分類を行う。
4. 問題カテゴリ、検出部位、重要度、原因候補を出力する。
5. `risk_scorer.py` で0から100のリスクスコアを算出する。
6. スコア内訳として、問題カテゴリ、重要度、部品特徴による加点を記録する。
7. `improvement_generator.py` で設計・金型・説明書・ユーザー体験の改善案を生成する。
8. `part_visualizer.py` でランナー上のリスクマップと対象部位ハイライトを生成する。
9. ランナー画像・特徴データ入力から、切り出し前の評価レコードを生成する。
10. Streamlit画面で表、グラフ、詳細分析、ランナー画像ベース評価、Markdownレポートを表示する。

## 検査フェーズ

現在の画面ではランナー状態・組立前を主対象にします。

| フェーズ | 値 | 主な確認対象 |
| --- | --- | --- |
| ランナー状態・組立前 | `runner_state` | ゲート位置、切り出し時の破損、小型部品、説明書工程 |

## 可視化の考え方

実在する商品画像や公式データを使わず、検査用の模式図をアプリ内で描画します。

- ランナー検査ビュー: 外枠、枝分かれしたランナー棒、不規則な部品形状、ゲート接続点、部品番号を描き、切り出し前の破損・ゲート跡リスクを表示する。
- ランナー画像・特徴データ入力評価: ランナー写真や模式図を入力し、画像から読み取った部品サイズ、ゲート位置、切り出し時負荷を指定して評価する。
- 対象部位ハイライト: 選択したフィードバックが指摘しているランナー上の部品またはゲート位置を強調表示する。
- 画像ベース評価: 生成済みランナー画像を見たときに、どの部品・ゲートが優先確認対象になるかを表とMarkdownで整理する。
- 問題カテゴリ表示: `breakage_risk` や `loose_joint` などの分類結果を色付きラベルで表示する。
- 修正ポイント表: 設計、金型、説明書、ユーザー体験の観点ごとに改善案と確認方法を表示する。
- スコア根拠表: カテゴリ、重要度、部品特徴による加点を表示し、判断理由を説明可能にする。

この可視化により、レビュー文だけでは伝わりにくい「どこが問題なのか」「どこから直すべきか」を画面上で把握しやすくします。

## デモとテスト

面接や説明時に使いやすいよう、アプリ内に任意フィードバック分析デモを用意しています。レビュー文、対象部位、検査フェーズ、架空の部品特徴を入力すると、その場で分類、リスクスコア、スコア根拠、改善案を確認できます。

品質確認として、標準ライブラリの `unittest` を使ったテストを用意しています。

- `tests/test_feedback_analyzer.py`: キーワード分類と部位検出の確認
- `tests/test_risk_scorer.py`: 設計特徴による加点とスコア上限の確認
- `tests/test_app_dataflow.py`: CSV、分析結果、優先度ランキング、行単位エラー耐性、レポート生成の確認
- `tests/test_actionable_fix_plan.py`: 部位別の具体的変更案とBefore/After検証計画の確認
- `tests/test_image_based_analyzer.py`: ランナー画像をもとにした再分析コメントの確認
- `tests/test_part_visualizer.py`: 架空ランナー模式図と選択部位強調の確認

GitHub Actionsでは、コンパイル、単体テスト、Streamlitの起動スモークテスト、README用画像生成を自動実行する想定です。

## 出力される改善案の例

- 軸径と受け側のクリアランスを見直し、可動時の摩擦を適正化する。
- 細いパーツの根元に補強形状を追加し、切り出し時の破損リスクを下げる。
- ゲート位置を目立ちにくい面へ移動し、処理しやすい接続にする。
- 説明書に注意アイコン、拡大図、左右比較図を追加する。
- 保持力不足がある場合は接続形状や摩擦面積を見直す。

## 実際の製品開発に応用する場合に必要になる追加データ

- 権利処理済みのユーザーレビューやアンケート
- 試作品レビュー、組み立て時間、失敗率などの検証データ
- 部品寸法、公差、材料、成形条件などの設計・製造データ
- 説明書の工程番号、図版、注意表示のメタデータ
- 権利処理済みのランナー写真、試作サンプル写真
- ユーザーレベル別の不満傾向
- 改善前後での満足度や破損率の比較データ

実運用では、企業秘密、個人情報、著作権、商標、契約条件を確認したうえで、利用可能なデータだけを扱う必要があります。

スコアの検証方法、Before/After比較、LLM/CAD連携の拡張設計は [validation_and_extension_plan.md](validation_and_extension_plan.md) に整理しています。

## 今後LLMを組み込む場合の拡張案

- `analyze_feedback(feedback_text)` の内部実装をLLM分類に置き換える。
- ルールベース分類結果をLLMへの補助入力として使い、出力の一貫性を保つ。
- 改善案生成で、対象部位、ユーザーレベル、過去の類似不満を踏まえた文章を生成する。
- 画像解析結果をLLMに渡し、ランナー画像上のゲート位置、細い部位、部品番号から改善仮説を生成する。
- Markdownレポートに優先度、想定工数、検証方法を追加する。
- LLM出力をそのまま使わず、カテゴリ候補やスコア範囲をバリデーションする。
- 機密データを扱う場合は、送信可能なデータ範囲、匿名化、ログ保存方針を明確にする。
